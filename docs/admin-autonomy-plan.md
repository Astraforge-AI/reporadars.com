# План: админка и автономное пополнение Reporadars

Дата: 2026-10-04. Статус: предложение для реализации, а не описание уже запущенных функций.

## Результат

Администратор управляет скиллами, коллекциями, статьями и заявками. Опубликованные записи появляются на сайте на русском и английском. Фоновая система находит новые `SKILL.md`, проверяет пакет, готовит описания и добавляет подходящие карточки по правилам публикации. Администратор видит происхождение каждой записи, причины решения и историю обновлений.

Автоматическая публикация означает публикацию метаданных и закреплённой ссылки на источник. Исполнение найденных инструкций и установка пакетов относятся к отдельному продукту и в этот план не входят.

## Что уже есть

- Next.js Pages Router, английские и русские маршруты, статическая сборка и адаптер Sites.
- Админка `/admin` и `/ru/admin`, серверный вход по email и проверка права администратора.
- SQLite-записи для скиллов, коллекций и статей; черновики, публикация, архив, защита от конфликтующих правок, заявки и журнал действий.
- Публичный `/api/content`, который отдаёт опубликованные редакционные записи. Публичный интерфейс пока читает другие, файловые источники данных.
- Go-импортёр: закрепление commit, ограниченное чтение архива, анализ полного каталога скилла, отчёт, подготовка EN/RU-описаний и экспорт метаданных после ручного решения.
- Текущий импортированный каталог пуст; реальный фоновый поиск, очередь, inference и автоматическая публикация не запущены.

Основание: [архитектура](architecture.md), [админка](admin-panel.md), [импортёр](skill-importer.md).

## Предлагаемые решения

| Часть | Решение | Причина |
|---|---|---|
| Интерфейс | Next.js, постепенное введение TypeScript, shadcn/ui для выбранных элементов | Используем существующий проект и сохраняем простой интерфейс |
| Сервер | Существующий Node.js API с расширенными контрактами | Уже реализованы вход, права, ревизии и редакционные операции |
| Хранилище | SQLite для первого запуска на одном сервере | Сохраняем текущие данные и уменьшаем объём миграции |
| Фоновые задания | Отдельный Go-worker и долговечная очередь в БД | Повторно используем анализатор; задания переживают перезапуск |
| Планировщик | Отдельный процесс постановки заданий под systemd | Поиск работает независимо от открытого браузера и веб-запросов |
| Production-каталог | Серверный Next.js с чтением опубликованных данных и обновлением кеша | Новые адреса и карточки появляются без изменения исходников |
| Статический прототип | Отдельная существующая сборка для Sites | Сохраняем `dist/client/index.html`, `dist/server/index.js`, `dist/.openai/hosting.json` и защищённые файлы адаптера |
| Описания | Адаптер модели с фиксированным JSON-контрактом | Провайдера можно заменить без изменения публикации |

Серверный вариант требует отдельной команды сборки и процесса Next.js. Сам статический Sites-адаптер не запускает API, worker или планировщик. ISR требует серверного окружения и не поддерживается статическим экспортом: [Next.js](https://nextjs.org/docs/pages/guides/incremental-static-regeneration).

Для первого запуска достаточно одного worker. PostgreSQL становится отдельной миграцией, если потребуются несколько серверов или нагрузочные проверки выявят ограничения SQLite. Redis не является обязательным для первой очереди.

Очередь и приватные отчёты разместить в отдельном хранилище конвейера. Основная БД с пользовательскими сессиями остаётся у Node.js API. Worker передаёт результат через ограниченный служебный интерфейс; обработчик модели и анализатор не получают доступ к пользовательским данным, SMTP и ключу публикации. Повтор передачи между этими хранилищами подтверждается идемпотентным идентификатором версии, а не общей транзакцией двух баз.

## План 1. Админка и публикация на сайт

### A1. Единый контракт публичного скилла

**Работа:** описать общий TypeScript/JSON-контракт и преобразование редакционных записей, исходных прототипов и импортированных карточек. Разделить состояние публикации, зрелость инструкции и вид проверки. Сохранить стабильные публичные ID, команды и пользовательский текст.

**Готово, когда:** обе локали получают одинаковый ID; черновик инструкции может быть публичной карточкой без заявления о проверенности; импортированный скилл содержит источник, commit, путь, лицензионные сведения и происхождение описания. Демонстрационные статьи сохраняют свою маркировку.

**Проверка:** контрактные тесты EN/RU и совместимости старых ID.

**Зависимости:** нет. **Область:** новый модуль контракта, `server/admin-service.mjs`, `src/data/imported-skills.js`, профильные тесты.

### A2. Сквозная публикация одного скилла

**Работа:** добавить серверную сборку Next.js отдельно от статической; реализовать слой чтения каталога и серверную загрузку списка и деталей по произвольному опубликованному slug. Прототипные данные переносить в БД отдельным управляемым импортом, сохраняя их статус и источники.

**Готово, когда:** созданный в админке скилл после публикации доступен по новому прямому URL в обеих локалях; черновик редакционной записи доступен только администратору; неизвестный slug возвращает локализованный 404.

**Проверка:** браузерный сценарий «создать → сохранить → опубликовать → открыть EN/RU» и проверка доступа к черновику.

**Зависимости:** A1. **Область:** `next.config.mjs`, `package.json`, новый слой чтения, `src/pages/[[...route]].jsx`, браузерный тест. Изменения сервера и интерфейса выполнять последовательно.

### A3. Обновление и снятие с публикации

**Работа:** связать опубликованные ревизии с публичным чтением и обновлением кеша. Использовать транзакционное событие публикации, чтобы ошибка доставки не терялась. В админке показывать разницу между решением редактора и подтверждённой видимостью на сайте.

**Готово, когда:** правка обновляет список и обе страницы; архивирование убирает карточку из выдачи и обрабатывает старый URL; временный сбой обновления кеша повторяется без потери события. Предлагаемая цель для серверного варианта — видимость успешной публикации в течение 60 секунд.

**Проверка:** публикация, изменение, архив, сбой кеша и повтор события; конфликт ревизий остаётся 409.

**Зависимости:** A2. **Область:** серверный store/service, обработчик событий, слой чтения и тест.

### A4. Простой рабочий интерфейс

**Работа:** боковая навигация «Скиллы / Коллекции / Статьи / Заявки / Пользователи»; списки с поиском, состоянием и пагинацией; отдельный редактор с EN/RU-полями. Добавить предпросмотр, указание несохранённых правок и понятные действия «Сохранить черновик», «Опубликовать», «В архив».

**Готово, когда:** ключевые действия доступны с клавиатуры; длинные формы читаемы на небольшом экране; конфликт сохраняет введённый текст; ошибки API показываются рядом с действием. Использовать небольшой набор [shadcn/ui](https://ui.shadcn.com/docs), адаптированный к текущим цветам и типографике.

**Проверка:** браузерные проверки форм, фильтров, клавиатуры и EN/RU.

**Зависимости:** A2; отображение результата публикации зависит от A3. **Область:** `src/admin/`, общие компоненты и профильные браузерные тесты. Список и редактор реализовать отдельными небольшими задачами.

### A5. Коллекции, статьи и заявки

**Работа:** по одному подключить коллекции и статьи к тому же публичному слою; добавить пользовательскую форму предложения скилла. Принятие заявки создаёт кандидата для обработки, а решение о публикации остаётся отдельным событием.

**Готово, когда:** коллекция ссылается на существующие доступные скиллы; статья имеет рабочий EN/RU-адрес; принятая заявка видна в очереди и не создаёт дубль при повторном запросе.

**Проверка:** отдельный сквозной тест для каждого вида контента и заявок.

**Зависимости:** A1–A3. **Область:** выполнять тремя последовательными задачами — серверный контракт, соответствующая страница, тест; не менять все экраны одним большим патчем.

### A6. Доступ и эксплуатация

**Работа:** сохранить серверную проверку доступа на каждом запросе; добавить отдельные права редактора, публикации и управления источниками по мере появления этих ролей. Подготовить HTTPS, почту, резервное копирование, восстановление и запуск процессов.

**Готово, когда:** обычный пользователь не получает редакционные данные; отозванное право прекращает доступ; восстановление из тестовой резервной копии проверено; секреты находятся вне исходников и публичной сборки.

**Проверка:** существующие auth/admin-тесты плюс новые роли; тест восстановления в отдельном окружении.

**Зависимости:** A3. **Область:** роли и проверки доступа — отдельная задача; инфраструктура и активация — отдельная задача. Развёртывание выполняется после отдельной авторизации.

**Контрольная точка админки:** один реальный разрешённый скилл проходит весь путь от черновика до публичных страниц, обновления и архивирования; статическая сборка и Sites-проверки продолжают проходить.

## План 2. Автономный поиск и добавление скиллов

Поток:

```text
Поиск GitHub / известные источники / заявки
                  ↓
           Долговечная очередь
                  ↓
     Закреплённый commit → Go-анализатор
                  ↓
       Дубли / структура / права / риски
                  ↓
         Описания EN + RU через модель
                  ↓
        Правила решения о публикации
          ↙              ↓             ↘
    Модерация     Публикация в БД    Блокировка
                         ↓
                Публичные страницы
```

### B1. Источники, кандидаты, версии и очередь

**Работа:** добавить таблицы источников и их политик, кандидатов, неизменяемых версий, заданий и событий. Отделить рабочий статус обработки от редакционного состояния. Предлагаемые состояния задания: `queued → running → succeeded / retry_wait / failed`; кандидата: `discovered → analyzed → described → ready / needs_review / blocked`.

Идентичность скилла: стабильный ID репозитория GitHub + путь каталога. Версия: commit + SHA-256 пакета. Повторное задание имеет уникальный ключ; похожие названия сами по себе не означают дубль. Для форков сохраняются отношения и отпечатки содержимого.

**Готово, когда:** повторный запуск создаёт одну версию; два worker не забирают одно задание одновременно; после перезапуска истёкшая аренда задания возвращается в обработку. Использовать атомарное получение задания, lease, heartbeat и ограниченные повторы.

**Проверка:** идемпотентность, конкуренция, авария до/после записи и восстановление.

**Зависимости:** A1. **Область:** отдельные миграции и модуль очереди с тестами; не смешивать миграцию с поиском GitHub.

### B2. Автоматический поиск

**Работа:** искать публичные `SKILL.md` через GitHub API; обходить разрешённые исходные репозитории и ссылки из отобранных каталогов. Ссылки из найденного текста становятся новыми кандидатами только после проверки адреса. Разбивать поисковые запросы на управляемые группы, хранить обходы и отмечать неполную выдачу.

GitHub ограничивает выдачу одного поиска, а code search имеет отдельные требования и лимиты. Поэтому один запрос не следует считать полным каталогом: [Search API](https://docs.github.com/en/rest/search/search#search-code). Соблюдать `Retry-After`, заголовки лимитов и условные запросы: [рекомендации GitHub](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api).

**Готово, когда:** расписание находит подходящий новый файл и ставит задание; повторный обход не создаёт дубль; лимит API откладывает работу и не вызывает бесконечные запросы. Первые реальные источники выбрать до пробного запуска.

**Проверка:** ответы API с несколькими страницами, неполной выдачей, 304, 403/429, ошибками сети и переименованием репозитория.

**Зависимости:** B1. **Область:** Go-модуль discovery, настройки источников, тесты API.

### B3. Фоновое сканирование существующим импортёром

**Работа:** обернуть существующий Go-анализатор обработчиком задания. Чтение всего пакета, commit и хеши сохраняются. Проверять структуру согласно [Agent Skills specification](https://agentskills.io/specification); отдельно учитывать лицензионные сведения, права на публикуемые данные и риски содержимого.

**Готово, когда:** worker обрабатывает разрешённый репозиторий и сохраняет ограниченный приватный отчёт; повреждённый архив, выход за пределы каталога, известные секреты и превышения размера получают объяснимый результат; найденный код не запускается. Отчёты и содержимое пакетов хранятся вне web root с политикой хранения.

**Проверка:** существующие Go-fixtures, ограничения архивов и задания с прерыванием скачивания. Статические проверки не следует представлять как доказательство безопасности или работоспособности.

**Зависимости:** B1–B2. **Область:** адаптер worker к importer, приватное хранилище отчётов и тесты.

### B4. Описания на двух языках

**Работа:** передавать модели только ограниченные свидетельства пригодного кандидата. Возвращаемый JSON содержит название, краткое описание, назначение, шаги, категорию, разрешения и замечания. Сохранять модель, версию prompt/schema, входной отпечаток и время генерации.

Текст `SKILL.md` является недоверенными данными. Модель обрабатывает его в контексте без файловых, командных, сетевых и MCP-инструментов. Идентификаторы и код не переводятся; недоказанные утверждения о поддержке агентов или результатах тестирования отклоняются.

**Готово, когда:** валидный ответ превращается в EN/RU-описание; невалидный ответ оставляет кандидата непубликованным; повторный запрос с тем же входом использует сохранённый результат. Изменённый prompt требует новой версии результата, а ручные правки редактора сохраняются отдельно.

**Проверка:** JSON-контракт, противоречивые факты, попытки prompt injection, отказ модели, таймаут и превышение лимита вывода.

**Зависимости:** B3. **Область:** адаптер провайдера, валидатор результата и тесты. Имеющийся Antigravity CLI не считается готовым inference-сервисом: вход и реальный запрет инструментов ещё требуют проверки; провайдера выбрать на пробной выборке.

### B5. Политика автоматической публикации

**Работа:** реализовать детерминированное решение по версии правил. Для начальной автопубликации источник должен быть разрешён для такого режима; пакет структурно корректен, права на публикуемые данные определены, блокирующих рисков нет, EN/RU-описания валидны, источник повторно проверен на том же commit и хеше. Структурный `qualityScore` и число GitHub-звёзд не заменяют эти условия.

Существующий ручной контракт запрещает модели выставлять `reviewer`, `rightsConfirmed` и `decision`. Автономный путь требует нового версионированного контракта с `reviewKind: automated`, `policyVersion`, свидетельствами и системным actor. Ручные решения и записи прежнего формата сохраняются; человеческая проверка не подделывается.

**Готово, когда:** пригодная карточка автоматически публикуется через тот же механизм, что ручная; спорный кандидат получает `needs_review` с причинами; заблокированный пакет не публикуется даже после общего одобрения источника. На сайте автоматическая обработка явно отличается от ручного ревью и runtime-проверки.

**Проверка:** таблица правил, повторный запуск, смена policy, обход через модель, заблокированный файл и сбой между решением и событием публикации.

**Зависимости:** A3, B4. **Область:** контракт v2, модуль policy, системные actor/права, адаптер публикации и тесты. Системный actor имеет отдельные ограниченные права и не использует человеческую email-сессию.

### B6. Управление автоматикой в админке

**Работа:** добавить разделы «Найденные скиллы», «Источники», «Задания». Показывать причины решения, состояние обработки, приватный отчёт, EN/RU-описания и разницу версий. Действия: проверить, опубликовать, отклонить, повторить задание, приостановить источник и остановить автопубликацию.

**Готово, когда:** редактор может решить спорный случай и увидеть его результат на сайте; повтор задания сохраняет историю; глобальная пауза прекращает новые автоматические публикации и не теряет очередь. Политика источника и снятие ограничений доступны отдельному праву.

**Проверка:** браузерный сценарий модерации, права, пауза во время обработки и конфликт ручных правок.

**Зависимости:** B1, B5, A4. **Область:** отдельные небольшие задачи для кандидатов, источников и заданий в `src/admin/`, API и браузерные тесты.

### B7. Отслеживание обновлений

**Работа:** периодически проверять новые commit известных источников. Смена commit при том же содержимом не создаёт лишнюю карточку. Изменившийся пакет проходит весь цикл заново; до успешного решения публичная ссылка остаётся закреплённой на предыдущей разрешённой версии.

**Готово, когда:** изменение создаёт новую версию и видимый diff; новые разрешения, исполняемые файлы или неясные права направляют обновление на модерацию; повторный обход не меняет ручную редактуру. Исчезнувший источник отмечается как недоступный с датой проверки; удаление карточки решается отдельной политикой.

**Проверка:** неизменённый пакет, изменение текста, повышение риска, исчезновение источника и восстановление предыдущей версии.

**Зависимости:** B5–B6. **Область:** планировщик обновлений, сравнение версий, сохранение предыдущей публикации и тесты.

### B8. Расписание, бюджеты и запуск

**Работа:** запустить планировщик и worker отдельными непривилегированными процессами. Предлагаемые стартовые настройки: поиск новых источников раз в сутки, проверка известных раз в 6 часов, один worker и ограниченная партия до 100 кандидатов за цикл. Значения настраиваются после пробного запуска.

Задать дневной бюджет запросов модели, количество кандидатов, предел повторов, размеры входов и время задания. Платные вызовы включать после настройки провайдера и бюджета. Сохранять счётчики найденных, уникальных, заблокированных, опубликованных и ожидающих модерации; время до видимости, стоимость, возраст очереди и время последнего успешного обхода. Уведомлять о существенных сбоях и требуемом действии.

**Готово, когда:** перезапуск восстанавливает очередь; исчерпанный бюджет приостанавливает дорогие этапы; сбой API/модели не публикует частичный результат; остановка автоматизации доступна администратору; тестовое восстановление данных завершено.

**Проверка:** длительный прогон в отдельном окружении, отказ API/модели, авария процесса, переполнение лимитов и восстановление резервной копии.

**Зависимости:** B5–B7, A6. **Область:** настройки и метрики — отдельная задача; процессы, секреты, резервное копирование и активация — отдельная задача.

## Порядок выпуска

1. **Рабочая ручная публикация:** A1–A3; один новый скилл появляется на сайте из БД.
2. **Удобная админка:** A4–A6; публикации, заявки и доступ проверены сквозными сценариями.
3. **Автоматические кандидаты:** B1–B4; поиск, анализ и EN/RU-описания работают в отдельном окружении, решения о публикации сохраняются для проверки.
4. **Ограниченная автопубликация:** B5–B6; разрешённые источники проходят путь до публичной карточки, спорные случаи видны редактору.
5. **Постоянная автономная работа:** B7–B8; обновления, бюджеты, пауза и восстановление проверены, область автопубликации расширяется по результатам пробной выборки.

Поиск и формирование очереди можно разрабатывать после A1 одновременно с интерфейсом. Подключение публикации зависит от работающего A3. План не требует автоматических изменений Git: карточки поступают в БД, а публикация кода остаётся отдельным процессом.

## Приёмка системы

- На разрешённом реальном источнике найден ранее отсутствующий скилл; после обработки его карточка доступна в обеих локалях и ведёт на конкретный commit.
- Повторный обход и повтор события публикации не создают дублей; новая версия проходит проверки заново.
- Нет выдуманного человеческого ревью, совместимости, лицензии или результатов исполнения. Неопределённые сведения отражены честно.
- Известные опасные тестовые пакеты блокируются, спорные случаи попадают в очередь, инструменты модели фактически запрещены.
- Ошибки модели, сети и БД, перезапуск worker и достижение бюджета дают объяснимый результат; очередь и предыдущие публикации сохраняются.
- Обычный пользователь и отозванный администратор не получают приватные отчёты и редакционные данные.
- Для затронутых модулей проходят Go-тесты/race/vet, серверные контрактные и браузерные тесты; статическая сборка и `npm run test:sites` остаются рабочими.

## Решения перед пробным запуском

Выбрать первые реальные GitHub-источники, список допустимых режимов лицензирования/атрибуции, провайдера модели с бюджетом, серверное размещение и параметры расписания. Эти параметры нужны для активации; план и локальные тесты можно подготовить заранее. Изменение хостинга, production-миграции, commit/push и развёртывание требуют отдельной авторизации.
